# UI localization

The board UI ships 42 locale files under `ui/src/i18n/locales/`. **Only `zh-CN` is
maintained here.** Every other locale carries the English text so the key sets stay
identical; translating them is out of scope for this repository's workflow.

## Layout

```text
ui/src/i18n/index.ts              i18next init, `t`, `useTranslation`, `changeLocale`
ui/src/i18n/locales.ts            locale loaders, DEFAULT_LOCALE = "en"
ui/src/i18n/locale-validation.ts  runtime validation (also used by a test)
ui/src/i18n/locales/en.json       source of truth for keys and English copy
ui/src/i18n/locales/<tag>.json    42 locales, key-identical to en.json
```

`locale-validation.ts` enforces, for every locale:

- the **same key set** as `en.json` (missing or extra keys fail)
- identical `{{placeholder}}` sets per string
- no injected `<script>`, event-handler attributes, `javascript:` / `data:` URLs
- no URL that the English string does not contain
- a length ceiling relative to the English string

`locale-validation.test.ts` runs the same check across every locale, so a broken
locale file fails CI rather than surfacing at runtime.

## Product name (white-label)

Locale files never hardcode the product name. They use the `{{brand}}`
interpolation, resolved from `interpolation.defaultVariables`:

```text
ui/src/i18n/brand.ts    resolveBrand / brandFor
                          precedence: VITE_BRAND_NAME_ZH (zh-CN only)
                                    > VITE_BRAND_NAME
                                    > test default "Paperclip"
                                    > shipped default "Gnzs"
ui/src/i18n/index.ts    seeds defaultVariables.brand and refreshes it on
                        `languageChanged`, so switching language changes the name
```

Tests intentionally resolve to **Paperclip**: master's assertions quote the copy it
ships ("Paperclip Cloud", "Paperclip Runner"), and they are about behaviour, not
about which name this build chose. Keeping the test-mode default at the upstream
name means a white-label build does not rewrite hundreds of upstream assertions —
and does not have to redo that after every upstream merge. `resolveBrand` takes
`testMode` as an explicit input, so both branches are unit tested.

Build a differently branded bundle without touching locale files:

```sh
VITE_BRAND_NAME_ZH="Acme" VITE_BRAND_NAME="Acme" pnpm --filter @paperclipai/ui build
```

Rules when adding copy:

- Write `{{brand}}` instead of the product name, including compounds
  (`{{brand}} Runner`, `{{brand}} Cloud`, `{{brand}}-managed`).
- Lowercase `paperclip` stays literal: npm scope `@paperclipai/*`, paths such as
  `/paperclip/instances/…`, API routes, protocol fields, and identifiers like
  `PaperclipLoading`.
- `brand.name` (value `{{brand}}`) exists for places that need just the name,
  such as the document title suffix and the default skill author.
- Do not put `{{brand}}` inside a URL, email address, or code sample.

Copy that never goes through i18n — labels, descriptions, toasts, aria-labels,
setup prompts — still needs the configured name. Use one of:

```tsx
// component: follows the active language
import { useBrandName } from "@/i18n";
const brand = useBrandName();
<span>{brand} Runner</span>

// lib helper / module table: resolved where it is read
import { brandName } from "@/i18n";
const label = `${brandName()} Runner`;
```

For a constant table that renders copy, prefer a getter so the read happens at
render time: `get label() { return brandName(); }`.

Leave these literal: HTTP headers (`X-Paperclip-*`), protocol fields
(`paperclip_session`, MCP `hostInfo`/`userAgent`), identifiers
(`PaperclipLoading`, `PaperclipRunner`), import paths, the lucide `Paperclip`
icon, `t(key, { defaultValue })` fallbacks, and any string the UI compares
against server output by equality or regex — renaming one side of such a pair
breaks the match silently, so it needs a coordinated change.

Verification: `ui/src/i18n/brand.test.ts` asserts the precedence table, the
test-mode value, and that no translated string leaks a raw `{{brand}}`.

## Adding a string

```tsx
// component
const { t } = useTranslation();
{t("responsibilities.emptyAdd", { defaultValue: "Add a responsibility" })}

// non-React module
import { i18n } from "../i18n";
i18n.t("responsibilities.emptyAdd", { defaultValue: "Add a responsibility" })
```

Rules:

1. **Always pass `defaultValue`, and keep it byte-identical to the `en.json`
   value.** i18next prefers the stored value, so a mismatch silently renders the
   stored copy instead of the literal in the code. A batch once shipped
   `"Record a reading"` in en.json while the code said `"Record a new reading"`;
   the only reason it was caught is that a test asserted the rendered text.
2. Reuse an existing key only when its stored English matches the code literal
   exactly. Otherwise add a new key — sharing a key between two different
   sentences has produced three separate regressions (`Add a responsibility`
   vs `Add responsibility`, two verdict labels, two Claude login messages).
3. Namespace after the feature (`responsibilities.*`, `routinePage.*`,
   `secrets.*`), then camelCase for the leaf. Keep siblings under one namespace.
4. A key must never be both a string and the parent of other keys
   (`responsibilities.areas` as a string vs `responsibilities.areas.name`).
   That collision breaks the JSON writer; rename one side.

### Plurals

Use i18next plural suffixes and register **both** keys:

```tsx
t("connections.setupFlow.sheetsReady", {
  count,
  defaultValue_one: "{{count}} sheet ready",
  defaultValue_other: "{{count}} sheets ready",
})
```

`en.json` needs `…sheetsReady_one` and `…sheetsReady_other`. Do **not** also add a
bare `…sheetsReady`: a bare key shadows the plural fallback and every count
renders the plural form.

## Do not localize

- User data interpolations: `{connection.name}`, `{accountLabel}`, `{login}`,
  `{row.displayName}`. These are values, not copy.
- `className`, `data-*`, `role`, `type`, `name`, `id`, `href`, `src`, `value`,
  `key`, `style`.
- CLI commands, protocol and scope names, permission enums, connector console
  field names, repository/branch names, URLs.
- Strings in `ui/src/lib/**`, `ui/src/hooks/**`, `ui/src/api/**` that participate
  in comparisons or persistence (e.g. `connection-identity.ts` labels, comparison
  against server-provided `acceptLabel`).
- Internal demo surfaces: `pages/DesignGuide.tsx`, `*UxLab.tsx`, `*Lab.tsx`,
  `components/design-sandbox/**`, `artifact-directions/**`.

## Two source-text assertion suites constrain the wording

These tests read the **source text** of UI files, so a `t()` wrapper around a
matched fragment fails them even when the rendered output is unchanged.

**1. `ui/src/lib/analytics/replay-masking.test.tsx`** (privacy)

For each entry it asserts a source fragment such as `{connection.name}` still
appears verbatim inside `ANALYTICS_MASK_CLASS`. Wrapping those interpolations in
`t()` removes the mask and lets user data reach session replay.

```tsx
// keep
<p className={cn("text-sm", ANALYTICS_MASK_CLASS)}>Remove {draft.name}?</p>
// breaks the suite and the privacy guarantee
<p>{t("pool.removeTitle", { name: draft.name, defaultValue: "Remove {{name}}?" })}</p>
```

Consequence: a handful of sentences stay English on purpose. If they must be
translated later, the fix is to teach the suite a data-attribute marker
(`data-analytics-mask`) instead of a literal fragment, then wrap them.

**2. `ui/src/pages/apps/chat/chat-ui-contract.test.ts`** (contract)

Asserts `title: "Run retry failed"` exists in `Inbox.tsx` and `LegacyInbox.tsx`.
The Inbox toast keeps the literal for that reason.

## Validation

```bash
cd ui && npx vitest run src/i18n/locale-validation.test.ts
cd ui && npx vitest run src/lib/analytics/replay-masking.test.tsx
```

Ad-hoc checks used while localizing (keep them out of the repo):

- **key coverage** — every `t("key")` in `ui/src` resolves in `en.json`
  (allowing `_one` / `_other`)
- **plural integrity** — a call using `defaultValue_one` has both suffixed keys
  and no bare key
- **defaultValue sync** — `en.json[key] === defaultValue` for every call

## Merging upstream

master does not maintain `en.json` (it is a 9-line placeholder there), and new
surfaces arrive as hardcoded English. When merging:

1. Take master's structure, DOM, and copy; keep `t()` around strings that were
   already localized, with `defaultValue` matching master's text verbatim.
2. Accept deletions when master replaces a component (the localization in it is
   gone with the file).
3. Restore localization that master's refactors drop, for example when rows move
   to a new file without their `t()` calls.
4. Re-run the full suite afterwards; the source-text suites above plus rendered
   assertions are what catch the regressions (`replacingACCOUNT_ID`, duplicated
   JSX from a union merge, a shared key with two different sentences).

A merge-local playbook with batch mechanics lives outside the repo
(`/tmp/opencode/m3/L10N-PLAYBOOK.md` in the session that produced it) — treat it as
a template, not a source of truth.
